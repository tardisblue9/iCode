# 文件访问沙箱

文件访问沙箱让 iCode 以及它替你运行的一切，都读不到你工作文件夹以外的文件。如果网页、文件或工具输出诱使模型去读无关的内容，比如你的文档、其他项目或 SSH 密钥，操作系统会直接拒绝这次读取。

沙箱默认关闭。支持 macOS 和 Linux（内核 5.19 及以上；Ubuntu 22.04 的较新内核和 Ubuntu 24.04 都满足），Windows 暂不支持。

## 开启

沙箱在 iCode 启动时确定，直到 iCode 退出都不会改变。在运行中的会话里修改设置，下次启动才生效。

- 仅本次启动：`icode --sandbox`（`icode run --sandbox …`、`icode acp --sandbox` 同理）。`--no-sandbox` 仅本次关闭。
- 仅本次启动，通过环境变量：`CHRYS_FILE_SANDBOX=1`。
- 每次都开：在 **设置 → 安全管控** 中打开 **文件访问沙箱（下次启动生效）**，或在 `~/.chrys/settings.yaml` 中加入 `sandbox: {enabled: true}`。

工作目录自己的设置（只有你开启了工作目录设置才生效）可以打开沙箱，但不能关闭。工作目录的设置试图关闭时，iCode 会在启动时提示，沙箱保持开启。

如果要求开启沙箱、但这台电脑无法提供，iCode 不会启动，并说明原因。若希望改为不带沙箱启动，把 **沙箱不可用时** 设为 `warn`（或 `CHRYS_FILE_SANDBOX_ON_UNAVAILABLE=warn`）；此时整个会话期间底栏都会显示 **⚠ 沙箱未生效**。

沙箱是一个独立的包 `icode-sandbox`。离线安装包自带它；从 PyPI 安装（`pip install icode-tui`、`uv tool install icode-tui`）则不包含。iCode 只在开启沙箱时才加载它，也只在装了它时才在**设置**和 `icode --help` 里提供这个开关。如果它没有安装，`icode sandbox status` 会提示；要求开启沙箱的启动按上面的规则处理：不启动，或在 `warn` 时不带沙箱启动。工作目录的设置要求开启沙箱而沙箱不可用时，只会警告：仓库不能让 iCode 无法启动。

## 能读什么

| 位置 | iCode 的工具和命令 |
|---|---|
| 本会话的工作文件夹 | 可读 |
| 系统目录、已安装的程序、`/tmp` | 可读 |
| 你的主目录和外接卷中的其他位置 | 不可读，除非你授权 |
| 凭证和浏览器数据（`~/.ssh`、`~/.aws`、`~/.gnupg`、钥匙串、Cookie 等） | 永远不可读，也无法授权 |

命令（shell、`grep`、`glob`、脚本）还能看到主目录中常见的工具链文件夹，比如 `~/.cache`、`~/.cargo/registry`、`~/.npm`，以及工作区上层目录里的项目文件（如 `pyproject.toml`、`package.json`），以保证构建和测试工具正常。在 Linux 上，iCode 启动时还不存在的工具链文件夹，要到下次启动后命令才能读取（`~/.cache` 和 `~/.local/share/uv` 会自动创建）。存放凭证的文件（如 `~/.npmrc`、`~/.pypirc`、`~/.cargo/credentials.toml`）依然不可读；如果某个工具要读这些文件夹里的其他配置文件，可能需要把它加入 `sandbox.files.commands.allow_paths`。

命令也不能把不可读文件夹里的文件移动或硬链接出来（例如 `mv ~/Documents/report.pdf .`），因为那样它在工作区里就变得可读了。出于同样的原因，在这些文件夹里删除或重命名文件也会被拒绝；工作区、已授权文件夹和工具链文件夹内不受影响。

## 能改什么

沙箱也限制命令和文件工具能改动什么，这样就没法留下内容，等之后在沙箱外运行。

| 位置 | 命令和文件工具 |
|---|---|
| 本会话的工作文件夹 | 可改 |
| 系统临时文件夹 | 可改 |
| 构建缓存，比如 `~/.cache`、`~/.npm`、`~/.cargo/registry` | 可改 |
| 其他位置 | 不可改，除非你授权 |
| shell 启动文件（`~/.zshrc`、`~/.bashrc` 等）、自启动（`~/Library/LaunchAgents`、`~/.config/systemd`）、`~/.gitconfig`、`~/.config/git`、程序文件夹（`~/.local/bin`、`~/.cargo/bin`、`~/bin`）、其他智能体的设置，以及 iCode 自身的设置和安装目录 | 永远不可改，也无法授权 |

所以有些命令在沙箱里会报 Operation not permitted，比如 `git config --global`、`cargo install`，请你在 iCode 之外自己运行。如果构建工具需要别的文件夹，在 `~/.chrys/settings.yaml` 的 **`sandbox.files.commands.write_paths`** 里添加；上面"永远不可改"的位置加了也不生效。你配置的 MCP 服务可以用 `write_paths` 单独放行自己的文件夹，写法和下面的 `read_paths` 相同。

回滚一个回合也遵守同样的规则：文件只会恢复到智能体现在能改动的位置。如果它路径上的某个文件夹后来被换成了指向外面的链接，这个文件不会被恢复，回滚结果会写明原因。

钩子、技能脚本和 MCP 服务也受同样的限制：钩子往主目录中这些文件夹以外的位置写文件，会收到 Operation not permitted。请让它写到工作文件夹或临时文件夹，或把它的文件夹加入 `sandbox.files.commands.write_paths`。

git 在仓库根目录、linked worktree 和 submodule 里都能用。如果工作文件夹是仓库的一个子目录，git 还要读仓库的其他部分，默认不开放；需要的话把仓库根目录加入 `sandbox.files.commands.allow_paths`。

## 模型需要其他文件夹时

在执行工具前会询问你的会话（手动审批）中，读取工作文件夹以外的文件会弹出审批对话框，并写明文件路径：

- **批准**：模型可以读取这一个路径，仅限这一次请求。
- **以后读取此文件夹时不再询问 → 本轮**：直到智能体回答完你这条消息前，该文件夹都可读。
- **→ 本会话**：该文件夹在本会话剩余时间内都可读，恢复会话后依然有效。
- **→ 此工作目录**：该文件夹在此工作目录的所有会话中都可读。

文件工具要改动上面列出的范围以外的内容时，对话框会询问写入。允许读取某个文件夹并不代表允许改动。批准只覆盖这一次请求所在的文件夹，也可以记住到本轮或本会话；写入授权不会超过本会话。命令不会弹出对话框，只会收到 Operation not permitted，授权之后才能写。上面"永远不可改"的位置，以及包含它们的文件夹（比如主目录、`~/.config`），申请写入会被直接拒绝。
- **拒绝**：模型会被告知你拒绝了。

通过 ACP 连接的编辑器中，同一请求提供 **Allow once**（仅这一次）、**Allow this folder for the session**（本会话允许此文件夹）和 **Reject once**（拒绝）。

你在消息里用 `@` 亲自指定的文件和文件夹，本轮内可直接读取，不再询问；用这种方式附加的图片即使在工作文件夹之外也能附加。指定整个主目录（`@~`）不会打开其中所有内容，凭证依然不可读。

在自动审批模式和 `icode run` 中，没有人可以询问，这类读取会被直接拒绝；模型会被告知在工作区内操作，或请你把该文件夹添加为工作目录。子代理沿用启动它的会话的授权，但不能申请新的授权。

## MCP 服务需要其他文件夹时

你配置的 MCP 服务可以读取自身程序所在的文件夹和工作区。要让某个服务读取更多内容，在智能体配置里为它加上 `read_paths`。其他服务不会因此获得权限，凭证文件夹依然不可读：

```yaml
tools:
  mcp:
    - name: notes
      transport: stdio
      command: notes-server
      read_paths:
        - ~/Documents/notes
```

## 用命令获取 API 密钥

用 `{{!command}}` 获取 API 密钥的命令（见[通过命令获取 API 密钥](./models.md#通过命令获取-api-密钥)）和其他命令一样受限，只能读命令可读的内容。只打印密钥的命令，或者调用自己保存登录状态的工具，都能正常工作。从主目录里的密码库读取的命令会失败，报错会说明沙箱已开启；把那个文件夹加到 `sandbox.files.commands.allow_paths` 下即可放行。钥匙串和其他凭证文件夹无法这样放行：开沙箱时请换一种方式提供密钥，例如在启动 iCode 前设置环境变量。

## 查看沙箱状态

- 沙箱生效时，底栏显示 **🛡**（降级或未生效时会显示文字警告）。点击它或按 **F7** 可打开沙箱面板：查看哪些位置可读、每个会话的授权（可 **撤销**），以及最近的拒绝记录。
- `icode sandbox status` 显示这台电脑是否支持沙箱（并实际检查能否生效），以及下次启动是否会启用。加上 `--session ID` 可查看某个会话的授权和沙箱事件，这些事件也保存在该会话的文件夹里。
- 要求开启沙箱时，`icode run` 和 `icode workflow run` 会输出一行说明沙箱是否生效；通过 ACP 连接的编辑器可在服务端能力信息中看到同样的状态。
- `icode sandbox grants` 列出已记住的授权；`icode sandbox grants --revoke ID` 删除一条。
- `icode sandbox probe` 启动一个受沙箱限制的进程，实际检查每一条边界。
- iCode 替工具执行的读取被拒绝时，`icode run`、`icode workflow run` 和每个会话的轨迹都会记录（`sandbox.access.denied`）；通过 ACP 连接的编辑器还会收到 `chrys/sandbox_denied`。命令自身的读取被拒绝时，由操作系统直接答复命令，只能从命令的错误输出看到。
- **不让路径出现在沙箱日志中：**在 **设置 → 安全管控** 中打开 **沙箱：在其日志和轨迹中隐藏路径**（`sandbox.files.audit.redact_paths`）。此后日志只保存路径的带密钥摘要，同一路径的摘要相同，你仍能在日志中追踪它。

## 局限

- iCode 自身的文件工具，是通过 Python 代码打开、创建、链接和修改文件所用的函数来限制的；工具也只能经 iCode 的受限路径启动程序。用其他方式打开文件的 Python 代码（例如直接用 `io.FileIO`）不受 iCode 进程的检查；iCode 自己的代码不这样做，并有测试保证不会这样做。智能体运行的命令始终由内核限制。
- 沙箱管控的是**读取文件**，不阻止命令通过网络发送数据；这一点请依靠审批。
- 改动限制针对命令和文件工具。工作文件夹里的内容都能改，其中之后会运行的东西（源码、`Makefile`、`.git/hooks`）会以你的身份运行。构建缓存也能改，工具之后可能运行其中的内容。
- 已在沙箱外运行的服务也能替命令改文件，不只是读，包括 macOS 的设置服务（`defaults write`）。
- **已在沙箱外运行的服务**仍可能通过本地 socket 被命令请求代为读取，例如 Docker、tmux 服务端，以及（Linux 上的）桌面或 systemd 用户会话。处理不可信内容时，不要让这些服务暴露在外。
- 在 macOS 上，沙箱开启期间 iCode 不能打开其他应用：打开新的 iCode 窗口、在访达中显示文件夹都不可用，请自己另开一个 `icode`。如果放开这一点，命令就能在沙箱外启动程序。
- 模型已经读到的内容是对话的一部分，会发送给你的模型服务商。
- 如果 iCode 自身运行的代码被攻破（例如恶意文档利用了解析器漏洞），它可以申请你本可以授权的文件夹。它运行期间读不到凭证和浏览器数据；但 iCode 自身进程的写入不受限，它可以改动 iCode 自身的文件或 shell 启动文件，改动的内容会在下次启动时以你的全部权限运行。
- 智能体在 shell 里再启动 iCode（如 `icode run`）时，那个 iCode 运行在智能体的沙箱里，读不到 iCode 的设置。
